# PAR-009 — Preserve drafts across external Party State updates

Status: `DONE`

Completed: 2026-08-15

## Implemented outcome

Follower wage and share edits are retained as client-local drafts while the
Party Sheet is open. Each draft records the Party State revision at which the
first input changed. An external state update rerenders authoritative content
without replacing those draft values and marks the draft stale when the live
revision has advanced.

Saving a stale draft submits its original base revision through the existing
authoritative store. The store therefore returns its established
`staleRevision` result and does not overwrite newer Party State. The draft and
warning remain visible after rejection. An explicit Discard action restores
the current authoritative values; a successful save clears the corresponding
draft. Closing the Party Sheet discards all client-local drafts.

Draft controls are available only while the current user remains an authorized
Party Sheet editor. Permission loss hides the controls without changing the
server-side authorization boundary.

## Files changed

- `module/apps/foundation-applications.mjs`: Captures follower drafts, overlays
  them during rerender, preserves base revisions, and implements save/discard
  lifecycle behavior.
- `templates/party-sheet.hbs`, `styles/hyp3e-utilities.css`, and
  `lang/en.json`: Add localized unsaved/stale status and the explicit Discard
  action without disturbing the follower grid.
- `tests/unit/application-shell.test.mjs`: Proves preservation, stale revision
  submission, and discard behavior.
- `tests/foundry/diagnostics/diagnostics.mjs`: Adds the two-client external
  update, stale-save rejection, and authoritative-restore gate.

## Verification

- `npm run check` passed with 94 automated tests, syntax checks, localization
  checks, and manifest validation.
- In Foundry 13.351 with `hyp3e` 4.0.3 and Foundry 14.365 with the official
  `hyp3e` dev 4.1.0 system, an authorized Player started a follower edit, the
  connected GM committed an unrelated external update, and the Player retained
  the exact draft inputs with a stale warning.
- The Player's stale save was rejected at its original revision and did not
  alter the authoritative follower wage or share. Discard then restored the
  GM-held values in both generations.
- The GM-side diagnostic received the complete Player result through the
  production socket path. Existing caller-identity and concurrent-write gates
  also remained green, with no diagnostic errors.

## Known limitations and follow-up

- PAR-010 owns automatic deleted-Actor cleanup.

No design-document change was required. No now-unused code remains.
