# PAR-001 — Implement the Party Sheet edit-permission policy

Status: `DONE`

Completed: 2026-08-14

## Implemented outcome

Party Sheet edit authorization is now a pure, immutable policy decision. A GM
is always authorized. A non-GM is authorized when their numeric Foundry role is
at least the configured threshold or their stable user ID is explicitly
granted. Missing users, malformed stored configuration, invalid roles, and all
other cases fail closed with a stable decision reason.

The policy uses the same setting validators as the permissions application and
is published through the production module API for reuse by UI controls and
GM-side mutation handlers.

## Files changed

- `module/party/party-permissions.mjs`: Adds permission reasons, structured
  evaluation, and a boolean helper.
- `module/core/bootstrap.mjs`: Publishes the policy through the module API.
- `tests/unit/party-permissions.test.mjs`: Covers every role/threshold pair,
  GM authority, explicit grants, denials, malformed configuration, and
  immutability.
- `tests/unit/compatibility.test.mjs` and
  `tests/foundry/diagnostics/diagnostics.mjs`: Verify API publication.

## Verification

- `npm run check` passed with 62 automated tests, syntax checks, and manifest
  validation.
- The permission matrix covers Foundry roles 1–4 against every threshold 1–4.
- Manual Foundry testing is not required for this pure policy; authoritative
  transport and multi-client behavior are the PAR-002 and Milestone 2 gates.

## Known limitations and follow-up

- UI read-only presentation and live permission refresh remain PAR-005 and

No design-document change was required.
