# REF-001 — Target Party Sheet external rerenders

Status: `DONE`

Completed: 2026-08-15

## Implemented outcome

The open Party Sheet now refreshes for shared Party State and permission
changes, and for create, update, or delete hooks involving a tracked member,
tracked follower, managed treasury Actor, or an Item embedded in one of those
Actors. Unrelated Actor and Item hooks are ignored.

Relevant hook bursts are queued through one microtask and coalesced into one
full ApplicationV2 rerender. The queue is registered once with the singleton
application, is removed on close, and refuses to render a closed sheet.
Reopening the already-rendered singleton uses the same preserving refresh path.

Before an external rerender, the application captures dirty ProseMirror
content and the active tab's panel scroll coordinates. Existing follower,
marching-note, supply, and party-note drafts remain separate from authoritative
Party State, while the active tab and its scroll position are restored after
rendering.

## Known limitations and follow-up

- REF-001 intentionally filters whole-application rerenders rather than
  introducing per-row DOM patching; the current Party Sheet size does not
  justify a second rendering abstraction.
- Treasury-specific rows and transfer-triggered refresh cases begin with
  TRY-001 and TRY-002 in Milestone 4.

No design-document change was required. No now-unused code remains.
