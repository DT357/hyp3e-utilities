# Foundry 14.365 / hyp3e 4.1.0 compatibility run

Date: 2026-08-14

Result: `PASS` through Milestone 1

## Environment

- Foundry VTT: 14.365
- System: `hyp3e` 4.1.0, `dev` commit
  `8d9aae354712087dacfea10fb0fd5a1f6beca8db`
- Module: Hyp3e Utilities 0.1.0 from the working tree
- SocketLib: v1.1.4
- Client: Codex in-app Chromium browser
- Clients used: one GM and one Player on distinct browser origins
- Data: disposable copy of the `hyp3e-test` world in an isolated Foundry data
  path

The production Foundry process and production world databases were not used or
modified. The isolated server used its own system copy and world databases.

## Runtime harness

The test-only module at `tests/foundry/diagnostics/` created synthetic Actors,
tokens, a scene, Active Effects, managed treasury candidates, and a small
ApplicationV2. It deleted the synthetic Actors and scenes after each
diagnostic. HUD-003 chat messages remained available for manual inspection in
the disposable world. The temporary data root, including those messages, was
removed after evidence capture.

## Notable observations

- An unlinked token did not retain a frozen base-Actor snapshot: a base HP
  update propagated until a synthetic HP update was made. The synthetic update
  remained isolated from the base Actor.
- SocketLib returned a clear error when the player temporarily had no connected
  GM. A later request succeeded after the GM reconnected.
- Foundry logged its standard minimum-window-size warning because the automated
  browser viewport was 1280 by 720. No diagnostic depended on viewport layout,
  and no module-originated exception was logged.
- The production foundation regression used an isolated server on port 33338.
  All six foundation result groups passed without a module-originated warning
  or error.
- The HUD rule regression used an isolated migrated world on port 33348.
  HUD-001 and HUD-002 passed through the production module API without a
  module-originated browser warning or error.
- HUD-003 ran in isolated worlds on ports 33350 and 33351. The first check
  exposed the v14 `messageMode: "gm"` compatibility requirement and failed
  closed without producing public messages. After correction, the official
  `hyp3e` dev 4.1.0 run passed every chat assertion without a new
  module-originated warning or error. Manual inspection confirmed readable
  reaction, save, and morale cards with unsafe markup displayed as text.
- HUD-004 ran against the official `hyp3e` dev 4.1.0 system in a fresh
  disposable data root on port 33353. All selection-controller assertions
  passed without a diagnostic error or module-originated browser warning or
  error.
- HUD-005 ran against the same official system in a fresh disposable data root
  on port 33355. UI actions produced two reaction messages, two explicit
  Sorcery save messages, and one morale message while reporting one expected
  missing-morale skip. Visual inspection confirmed readable responsive rows,
  health bars, and long-name ellipsis at 1280 by 720.
- HUD-006 ran against the official `hyp3e` dev 4.1.0 system in a fresh
  disposable data root on port 33357. Centered defaults, the Pointer Events
  handle, persisted drag coordinates after overlay recreation, reset, resize
  clamping, and oversized off-screen recovery all passed. Visual inspection
  confirmed the 704-pixel HUD remained readable inside the 1280-by-720
  viewport. Foundry automatically repaired the two archived disposable system
  pack copies before loading them; the world and every module diagnostic then
  completed successfully.
- HUD-007 ran in a fresh disposable data root on port 33359. Five Actor updates
  spaced 10 milliseconds apart produced one final model notification. Three
  enable/disable cycles, two destroy/restart cycles, and repeated starts kept
  one overlay and completed without a diagnostic error.
- HUD-008 ran against the official dev 4.1.0 system in a fresh disposable data
  root. Every accessibility, localization, disabled-state, unavailable-action,
  no-chat, and localized-error-notice assertion passed with SocketLib v1.1.4.
  The final automated suite contained 57 passing tests.
- PAR-001 and PAR-002 ran against the official dev 4.1.0 system in a fresh
  disposable data root on port 33368 with one GM and one Player client. The
  production permission matrix passed. The mutation handler used the
  SocketLib-derived Player ID, executed exactly once on the active GM across a
  duplicate request, rejected an unknown payload field as `invalidRequest`,
  and matched the independent raw Foundry socket sender. The accompanying
  automated suite contained 68 passing tests.
- PAR-004 ran against the official dev 4.1.0 system in a fresh disposable data
  root on port 33370 with one GM and one Player client. Two revision-0 writes
  serialized into one success and one stale rejection with fresh state. The
  retry committed revision 2, the Player and GM states matched with both Actor
  UUIDs, and the independent sender ID matched the Player. The accompanying
  79-test suite covered successful and failed compensation paths.
- PAR-005 ran against the official dev 4.1.0 system in the reusable disposable
  Milestone 2 root on port 33372. Singleton identity, six tabs, settings-menu
  routing, external refresh, close cleanup, and replacement all passed. The
  first run exposed the action-target mismatch also seen in v13; the corrected
  run switched tabs and passed beside the 80-test automated suite.
- PAR-009 reused that root on port 33372 with a connected GM and authorized
  Player. An unrelated GM mutation preserved the Player's exact follower draft
  and displayed the stale warning. Saving at the original base revision was
  rejected without overwriting authoritative wage/share data, and discard
  restored the current values. GM and Player diagnostics had no errors beside
  the 94-test automated suite.
- PAR-010 completed that root on port 33372. Deleting a tracked member and
  follower pruned shares, wage, and marching metadata with one revision each;
  synthetic token deletion was inert and the deleted treasury binding remained
  exact. The complete connected GM/Player Milestone 2 regression then passed
  without errors beside the 98-test automated suite. The stopped disposable
  root and its module junctions were removed; the installed v14 application was
  untouched.
- MAR-002 ran in a reusable disposable Milestone 3 root on port 33374 against
  the official `hyp3e` dev 4.1.0 system. Connected GM and authorized Player
  clients passed four-group rendering, enriched and missing rows, button and
  drag/drop movement, stale note-draft preservation, original-revision
  rejection, discard recovery, responsive wrapping, raw sender identity, and
  cleanup. All diagnostics completed without errors beside the 103-test suite.
- MAR-003 reused the root on port 33374. The official dev 4.1.0 system created
  one saved-revision public card with ordered Front, Middle, and Rear ranks,
  ordered Actors, an empty Rear row, and a hostile note rendered only as text.
  The connected Player observed all three ranks, and every diagnostic passed
  beside the 105-test suite.
